Customer 360

MCP fleet architecture for the Commercial Credit Brain

The Commercial Credit Brain is the orchestrating intelligence; the MCP fleet is the tool layer it navigates, built one server at a time rather than big-bang. The shipped credit-memo tools (Boom, AFS, experience-mcp) were the first set, deal-level underwriting. This Customer 360 / Early-Warning fleet is the next, relationship-level monitoring. Each server that comes online widens what the brain can reach, so the brain gets smarter every time a tool ships. Policy and governance are designed in from day one, not bolted on: the SR 11-7 deterministic wall, run-as-user identity, per-call audit, DRAFT-until-attested. And the fleet is enterprise-bank scalable on AWS, remote-hosted in org-controlled infrastructure so untrusted, high-churn MCP code never touches an analyst's machine.

Surface
One MCP server, many swappable surfaces: Claude MCP App widget, Agentforce-in-FSC twin, hosted Next.js, M365 / Copilot, ChatGPT Apps. Built to the strict MCP Apps subset, portable across hosts.
Scale
Remote-host the fleet in org-controlled AWS infra (Bedrock AgentCore Runtime or ECS / Fargate in a private VPC). The governance unit becomes the environment plus a promotion gate.
Stage
Stage 0 reference build. Inter-MCP fleet pattern shipped and proven in code; Customer 360 read spine in build. Honest gates stated, not hidden.

How a tool call actually resolves

Mechanics · 1 of 2

One banker question becomes one tool call. The fleet composes the answer in code, and the regulated number is computed before the model ever sees it. The aggregation MCP is itself a client to the system MCPs.

07

Transport, hosting, and why detection is a job

Runtime

All three shipped connectors are Next.js + mcp-handler, dual-transport stdio + streamable-HTTP. Stdio for local / embedded use; streamable-HTTP for the remote governed connector URL that Cowork / Claude / Agentforce attach to.

  • Stateless connectors, stable resource URIs. Widgets are served at a content-hash-free ui://<bank>/<name>.html URI so the host caches the widget at the connector level. Cross-source widgets live with whoever owns the join (experience-mcp), because external iframes are blocked by the host, so the fleet renders its own bank-branded UI.
  • Public-but-governed URLs. Today: SSO / deployment-protection off so the connector URL is reachable, writes gated behind EXPERIENCE_ALLOW_WRITES, run as a real Salesforce user (client-credentials External Client App). The connector is bank-neutral: the bank name is a BANK config block, env-swappable per tenant.
Async + governor limits: detection is a job, the screen just reads

Computing an EWS read live (AFS servicing + nCino covenants + FSC deposits + Boom ratios) inside a single realtime Salesforce response would blow SOQL and CPU governor limits the moment you fan it across a portfolio. So the architecture splits compute from render: EWS detection runs as a Queueable / Batch Apex job, server-side, on the deterministic reads, and writes pre-computed results (fired signals, cushion %, severity score) back to records. The dashboard reads those pre-computed fields; no heavy join at view time, so the portfolio view scales to the whole book.

CDC repaints hands-free. Change Data Capture (the shipped CreditMemoCDC__chn channel over LLC_BI__Product_Package__ChangeEvent + LLC_BI__Loan__ChangeEvent) drives an lightning/empApi LWC that calls getRecordNotifyChange + RefreshEvent: the screen moves on a write without a manual refresh (verified live). One pre-demo ritual: warm the CDC channel (~1-3s warm vs ~15-30s cold).

The fence holds in async too. A fired trigger raises a flag; it never moves a grade. EWS detects, grades, ranks, and routes; a human classifies and decides (Pass / Watch / Special Mention / Substandard / Doubtful / Loss). Severity (Low / Med / High / Critical) is decision-support, captured proposed-not-committed; it becomes real only when the authorized human commits via record_decision, with classification authority enforced server-side against the acting user.

08

The data spine, the Snowflake ledger, and per-call PII audit

Data

What makes the joins valid and the decisions defensible: one spine every node keys on, end-to-end lineage, and a decision ledger that records why every number was committed.

One spine: Product Package + Account. Every node keys on this pair. The Account is the relationship anchor (FSC FinServ__* + nCino LLC_BI__Account); the Product Package is the deal anchor that nCino, the credit memo (LLC_BI__Credit_Memo__c / the cm_* rich-text fields), AFS servicing, and IRIS grades all hang off. experience-mcp's joins are valid only because both sides resolve to the same keys. A fired EWS signal rolls up to the obligor / relationship group, never an isolated loan tile.
Lineage you can trace end to end: Boom → IRIS → nCino. The raw spread is computed in Boom; the rating / PD / covenant grade is published by IRIS on Snowflake (zero-copy); the governed result is written back to nCino as structured cm_* narrative fields plus the nFORMS HTML memo, DRAFT until finalized and attested, then one deliberate end-sync commit, never per-edit write-through.
The Snowflake decision ledger + per-call PII audit. experience-mcp owns the system-of-record for why a decision was made. Every tool call that touches borrower data writes an audit row: the run-as integration user EXECUTES, the human RM is STAMPED (actingUserName / actingUserId), with agent-provenance (model + version) as the future third leg of the audit triple. record_decision / log_audit_event / recall_decisions are the ledger surface.
The whole posture, in one line

Inside the org, queries run WITH USER_MODE so CRUD / FLS / record-sharing auto-apply to the caller; no anonymous service account, the caller lands in the audit trail. The single admin god-mode path (cross-user read) is explicitly enabled and fully logged. That is the whole posture: the regulated number is computed in code, the LLM never computes it, and every borrower-data touch is attributable.

09

Identity and auth: two legs of provenance, run-as-user on reads

Identity

The read path is an upgrade over the memo, not a copy of it. The shipped credit memo (experience-mcp / sfClient.js) runs as a single client-credentials service account, where actingUser is an audit stamp on writes only, never a sharing identity. Customer 360 deliberately upgrades this: it runs as the user.

  • Reads, run-as-user OAuth. External Client App, OAuth 2.1 + PKCE, mcp_api + refresh_token scopes; every SOQL / Apex path runs WITH USER_MODE so CRUD / FLS / record-sharing auto-apply to the caller. No anonymous service account; the calling user lands in the audit trail. Correct for a relationship cockpit that reads far more of the customer than a single deal does.
  • Writes, the SR 11-7 two-leg provenance. The gated write path uses a client-credentials run-as integration user that EXECUTES, with the acting user STAMPED (actingUserId / actingUserName, threaded on every write per the plugin↔MCP contract). The agent model + version is the third leg. Two legs of identity plus one of model = full provenance on every committed number.
  • Admin god-mode is a separate, explicitly-enabled, fully-logged cross-user read path, the one place the run-as-user boundary is intentionally bypassed. Permissioned plus audited.
  • Per-user token isolation must be verified before any borrower-PII pilot. On custom / Team connectors, confirm the OAuth token is issued per user, not shared per org; a shared token would mean every user sees every book.
Honest caveat, live-verified 2026-06-28

In the bankinggpt sandbox the internal OWD is permissive (ReadWrite Public on most objects), so run-as-user does not narrow visibility in this org; persona book-narrowing is UX, not a security boundary here. Real least-privilege enforcement comes from the bank's production OWD (Private + Grant Access Using Hierarchies). We present persona views; we do not claim we enforce least privilege in the sandbox.

10

Enterprise scale on AWS: the environment is the governance unit

Scale

Threat model, stated plainly: an MCP server is arbitrary code running as the user. It must never run on an analyst's machine. Remote-host the fleet in org-controlled infrastructure.

Landing pattern A
Bedrock AgentCore Runtime
Per-session microVM, isolated then terminated after use. Accenture Track 2 is already standing up an AgentCore AWS environment, so the v4 target has a concrete home.
Landing pattern B
ECS / Fargate in a private VPC
The fleet runs behind owned egress and IAM. Source MCPs (Boom, AFS, IRIS, CapIQ) hold no session state, so they scale out flat behind the per-session microVMs.
  • The governance shift. The unit of control becomes the environment + a promotion gate, not per-connector approval. You don't vet each connector by hand; you vet the environment it's promoted into. This is what makes untrusted, high-churn MCP code safe at bank scale.
  • Residual risk relocates to ownable surfaces: VPC egress + IAM, both owned by the bank, both auditable.
  • The SR 11-7 wall holds across all of it. Every regulated number is computed deterministically in code (covenant.js grade = actual × threshold; boomFinancials.js server-to-server fetch, the ratio never round-trips through the LLM). The decision ledger and audit trail live in Snowflake (record_decision / log_audit_event). DRAFT-until-attested; the cockpit concludes and routes, a human commits.
The v4 argument, in one frame

Remote-host the fleet in org-controlled infrastructure so untrusted, high-churn MCP code never touches an analyst's machine. The governance unit becomes the environment plus a promotion gate; egress and IAM are owned by the bank, not the tool author. This is not hypothetical: Accenture Track 2 is already standing up an AgentCore AWS environment.
